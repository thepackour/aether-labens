# Aether Labens

> *aether labens* — 라틴어로 "미끄러지는 에테르"

**Aether Labens**는 여러 플레이어가 하나의 거대한 맵을 함께 쓰는 실시간 슬라이딩 퍼즐 웹게임입니다.
플레이어는 방향만 고를 수 있고, 한번 움직이기 시작하면 무언가에 부딪힐 때까지 멈추지 않고 미끄러집니다.

무대는 우주처럼 보이지만 우리가 아는 우주는 아닌, 에테르로 가득 찬 **미지의 차원**입니다.
떠다니는 블록과 결정체 사이를 미끄러지며 길을 찾는 것이 이 게임의 전부이자 핵심입니다.

> 🚧 기획 단계의 프로젝트입니다. 아래 내용 중 일부는 확정되지 않았고, 미정인 부분은 따로 표시해 두었습니다.

## 게임 소개

보드게임 *리코셰 로봇(Ricochet Robots)* 의 "벽에 닿을 때까지 미끄러지는 이동"을 바탕으로 한 퍼즐 게임입니다.
리코셰 로봇이 한 판의 보드 위에서 최소 수를 겨루는 게임이라면, Aether Labens는 그 규칙을 **모두가 함께 쓰는 넓은 오픈 월드**로 옮겼습니다.
미끄러지는 이동감은 *TOTM(Tomb of the Mask)*, 여러 사람이 한 맵에 모이는 감각은 *Agar.io*, 매일 새로 열리는 과제는 *Wordle*식 데일리 챌린지에서 영향을 받았습니다.

- 모든 플레이어가 **같은 맵**에 있습니다. 다른 플레이어도 내 경로의 장애물이자 발판이 됩니다.
- 카메라는 **플레이어에 고정**되어 있어, 미끄러져 움직여야만 맵의 다른 곳을 볼 수 있습니다. 이동이 곧 탐험입니다.
- 누군가 블록을 부수거나 옮기면 그 변화가 **모든 플레이어에게 실시간으로** 보입니다.
- 한 번의 이동은 짧지만, 어디서 멈출지를 계산하는 것이 퍼즐입니다.

## 핵심 규칙

1. 플레이어는 상·하·좌·우 중 한 방향을 고릅니다.
2. 고른 방향으로 **장애물에 부딪힐 때까지** 미끄러집니다. 중간에 멈출 수 없습니다.
3. 멈추는 조건은 다음과 같습니다.
   - 벽이나 블록에 부딪힘 → 바로 앞 칸에서 멈춤
   - 다른 플레이어에 부딪힘 → 그 플레이어 바로 앞 칸에서 멈춤
4. 이동 중 지나간 칸의 재화와 아이템은 획득합니다.
5. 이동 결과는 서버가 계산합니다. 클라이언트는 방향만 보내고, 서버가 계산한 결과를 그대로 그립니다(서버 권한형).

> 원안에 있던 "붙잡는" 칸(거미줄·물웅덩이)은 삭제했습니다. 플레이어는 벽·블록·다른 플레이어에 부딪혀야만 멈춥니다.

**미정**
- 일일 횟수의 정확한 규칙과 수치(색상 블록 이동에 쓰이는 것은 확정, 플레이어 이동에도 적용할지는 미정)
- 플레이어끼리의 상호작용 규칙(밀기, 막기 등)
- 데일리 챌린지의 구체적인 형태

## 블록

테마는 **우주 / 미지의 차원**입니다. 블록은 충돌 동작 기준으로 나누고, 겉모양은 이 테마에 맞춥니다.

| 종류 | 동작 | 디자인 |
| --- | --- | --- |
| 빈칸 | 그대로 지나갑니다. | 검은색 또는 매우 어두운 보라색 배경 |
| 벽 | 부딪히면 앞 칸에서 멈춥니다. 2×1, 3×1 같은 긴 벽도 별도 종류 없이 벽에 포함됩니다. | 폴리곤·네온·테크 스타일. 이웃한 벽 칸끼리 하나로 합쳐져 보입니다. |
| 금 간 블록 | 적힌 숫자만큼 부딪히면 부서져 길이 열립니다. 부서질 때 재화나 아이템이 나올 수도 있습니다. | 글리치 스타일 |
| 색상 블록 | 플레이어가 움직일 수 있는 블록입니다. **카메라 안에 보이는 블록만** 움직일 수 있고, 움직일 때마다 일일 횟수가 차감됩니다. | 움직일 수 있는 블록이라는 게 한눈에 드러나는 디자인 |

긴 벽은 칸마다 벽으로 저장하고, 렌더링할 때 이웃한 벽 칸을 이어 그려서 하나의 덩어리처럼 보이게 합니다.

## 재화와 아이템

- **재화**: 매일 맵 곳곳에 랜덤으로 생성됩니다. 미끄러지며 그 칸을 지나가면 획득합니다.
- **아이템**: 획득한 뒤 소모해서 특수 효과를 냅니다. 금 간 블록을 부술 때 나올 수도 있습니다.

**미정**
- 재화의 생성량과 분포
- 아이템 목록과 효과

## 공유 월드

- 맵은 하나이고 모든 플레이어가 함께 씁니다.
- 한 플레이어의 행동(블록 파괴, 블록 이동, 재화·아이템 획득)은 같은 구역을 보고 있는 모든 플레이어 화면에 즉시 반영됩니다.
- 여러 사람이 같은 블록과 칸을 동시에 건드리기 때문에 **동시성 제어가 중요**합니다. 동시에 여러 이동 요청이 들어와도 결과가 엇갈리지 않도록, 서버는 이동을 **하나의 큐에서 순서대로** 처리합니다.
- 맵은 **유저가 늘어나거나 특정 조건을 달성하면 확장**됩니다.
- 초기 개발에서는 맵을 고정해서 쓰고, 맵 자동 생성과 확장은 이후 과제로 둡니다.

## 맵 구조

맵은 **32×32칸 크기의 청크** 단위로 나누어 저장하고 전송합니다. 맵 확장은 청크를 덧붙이는 방식으로 할 수 있습니다.

```
청크 하나 = 32 × 32 = 1024칸 = 1024바이트
인덱스    = y * 32 + x
```

각 칸은 **1바이트**입니다.

```
bit:  7 6 5 4 | 3 2 1 0
      종류      | 내부 값
     (4비트)    | (4비트)
```

- **블록 종류(상위 4비트)**: 빈칸, 벽, 금 간 블록, 색상 블록 등 동작이 다른 종류만 구분합니다.
- **내부 값(하위 4비트)**: 종류마다 뜻이 다릅니다.
  - 벽: 겉모양 번호
  - 금 간 블록: 남은 내구도(1~15)
  - 색상 블록: 색 번호

이렇게 하면 청크 하나가 1KB로 작아서 저장과 전송이 가볍고, 충돌 계산은 상위 4비트만 보면 됩니다.
종류가 16개를 넘거나 내부 값이 더 필요해지면 칸당 2바이트로 늘리는 방안을 검토합니다(현재는 보류).

블록 종류 번호의 정확한 배정과, 재화·아이템을 칸 데이터에 넣을지 별도로 둘지는 아직 확정하지 않았습니다.

## 실시간 동기화

- **클라이언트 → 서버**: 모든 요청은 HTTP(REST)로 보냅니다. 예: 이동 요청은 방향만 담아 보냅니다.
- **서버 → 클라이언트**: 맵 변화는 **SSE(Server-Sent Events)** 로 밀어 줍니다.
  - 클라이언트는 지금 보고 있는 주변 청크(최대 9개)를 구독합니다.
  - 이벤트 예시: 플레이어 이동, 블록 변경, 재화·아이템 생성, 재화·아이템 획득
  - 이벤트마다 증가하는 ID를 붙여, 연결이 끊겼다 다시 붙으면 놓친 이벤트부터 이어 받습니다. 너무 오래 끊겼으면 청크를 통째로 다시 받습니다.

브라우저에는 `EventSource`가 기본으로 있어서, 웹게임에서는 SSE를 별도 라이브러리 없이 쓸 수 있습니다.

## 기술 스택

**웹 게임으로 먼저 개발**하고, 여유가 되면 나중에 웹 코드를 **Capacitor**로 감싸 앱으로 출시합니다.

| 영역 | 선택 | 비고 |
| --- | --- | --- |
| 백엔드 | Spring Boot | 서버 권한형 이동 계산, 단일 이동 큐 |
| 프론트엔드 | Vue | 게임 화면 밖의 UI(로그인, 상점, 메뉴 등) |
| 게임 화면 | PixiJS 같은 Canvas/WebGL 렌더러 | 타일 맵 렌더링, 미끄러짐 애니메이션, 네온·글리치 효과 |
| 실시간 | SSE | 서버 → 클라이언트 단방향으로 충분하다고 판단 |
| 앱 출시 | Capacitor | 웹 코드를 그대로 감싸는 방식 (React Native는 쓰지 않음) |
| DB | 미정 (예: MySQL) | 청크당 한 행, 칸 데이터는 1024바이트 BLOB |
| 배포 | 미정 | |

## 후순위 기능

핵심 플레이가 완성된 뒤에 검토할 기능입니다.

- **상점·업적**: 카메라 줌아웃, 일일 횟수 회복·증가, 외형 꾸미기
- **이벤트**: 최적 경로 찾기, 일일 횟수 베팅, 재화 대량 생성, 협동 이벤트
- **학교 대항전**

## 배경

이 게임 규칙은 원래 팀 모바일 앱 프로젝트를 위해 기획했던 것입니다(당시 가제 *Puang's Christmess*).
팀 프로젝트의 규칙이 바뀌면서, 처음 기획한 원안 규칙을 개인 프로젝트인 웹게임으로 따로 이어서 만들고 있습니다.
